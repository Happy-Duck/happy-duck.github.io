## My part

My part is the prop for the final puzzle: a keg with a keypad set into it. Solve the rest of the hunt, type the answer on the keypad, and a solenoid lock lets a drawer tip out of the keg. I designed the circuit and wrote the Arduino code.

It did not start as a drawer. The first plan was a sticker dispenser: the right code would make a servo arm push out a sticker as the prize. That is the version the paper prototype tested. The dispenser was dropped, and the keg became a locked drawer, the keg safe of the schematic below.

The class had me set two learning objectives. One was designing a prop to last through many players over many sessions. The other was electronics, because, as I wrote at the start of term, "as a computer scientist, my work largely involves abstract software, but I am interested in being able to combine that skill with hardware components to create more physically tangible experiences."

## The circuit

<Figure src="/media/courses/info-418/keg-safe-breadboard.webp" alt="A breadboard layout: an Arduino Uno wired to a TIP120 transistor, a solenoid, a bench power supply, a red and a green LED with resistors, a diode, and a piezo buzzer" caption="An earlier layout of the keg safe in Tinkercad. The circuit has changed since." />

The parts, and why each is there:

| Part | What it does |
| --- | --- |
| Arduino Uno | Reads the keypad and decides whether the code is right. |
| 4 by 4 keypad | Eight wires, four rows and four columns, scanned to find which key is down. |
| 12 V solenoid | The lock itself. It needs far more current than a pin on the Arduino can supply. |
| TIP120 transistor, 1 kΩ resistor | The Arduino switches the transistor, and the transistor switches the solenoid's 12 V. |
| Diode across the solenoid | A coil pushes back when it is switched off. The diode gives that current a path that is not the transistor. |
| Red and green LEDs, 220 Ω each | Two status lights. |
| Piezo buzzer, small transistor | Sound, driven the same way as the solenoid but at a smaller scale. |
| 0.1 µF capacitor | Across the 12 V supply, to smooth it. |

## The first week on the bench

I kept a log while the first prototype came together, from 21 to 27 October. It starts with the blinking-light tutorial from Arduino and ends with the lights, the speaker, and the solenoid lock (wired from Adafruit's schematic) all answering a typed code. Along the way:

| What went wrong | Why | The fix |
| --- | --- | --- |
| An LED would not blink | The LED was dead. The board's own LED blinked, so the code was fine. | A new LED. From the log: "always test LEDs before using them." |
| Typed input, standing in for the keypad, did nothing | The serial port was never started | `Serial.begin()` in setup |
| The lights were dim | Resistors far stronger than needed | 220 Ω |
| Ran out of ground pins | Three parts needed one, and the Uno has two | The breadboard's rail as a shared ground |
| The speaker played only the last note of a tune | Each note cut off the one before it | A function that plays a note for a set time, then pauses |
| The Arduino would not connect | A different USB port from the day before | The first port |
| Typed codes were slow to answer | The code read whole strings | Read one character at a time, which is also how the keypad will send them |

## Built to last

A prop in a room is handled by many players over many sessions, and most of my building before this class had been prototypes, not made to last. The durability plan, written at the paper prototype stage:

| What could fail | The plan |
| --- | --- |
| The symbols on the keypad wear off | A metal keypad of the kind payphones use |
| Wires come loose | Screw terminal shields: the wires are screwed down, but can still be changed in late testing, which soldering would not allow |
| Spilled drinks | The electronics sealed under a 3D printed false keg top, and the keypad set in, away from spills |
| A power cut | A battery bank between the wall and the Arduino, as a small UPS |

Then the first prototype went through a stress test:

- The solenoid was switched 1,000 times, on for 100 ms in every 400 ms, and stayed responsive. That is far more often than the drawer will open in the room. The lock piece jiggled when it pointed up, and the whole thing shook, so it should be mounted sideways or facing down, on something solid like the keg itself rather than a printed platform.
- Nothing grew noticeably warm, the flyback diode and the transistors included. The lights and the speaker went through the same test with the same result.
- The Arduino's power was pulled and restored 25 times, across its three states (waiting, right code, wrong code). It came back working every time.

## Play-testing

The paper prototype was play-tested while the keg was still a sticker dispenser. It went as intended: the players typed the code and got their sticker. They got the code right on the first try, though, and never went near the keg until they had solved everything else. They also said they were unsure what each puzzle was for, and how the puzzles came together.

Meeting the keg early, and trying a code on it, would have shown them what shape the final answer takes. The one change the playtest suggested was where the keg stands: somewhere players meet it sooner.

The paper sticker had a problem of its own. Players could not tell whether it was a sticker, a coin, or some other trinket: a cut-out piece of paper does not look like a sticker when everything around it is paper too.
