## The idea

Casual sports fans have a hard time keeping up with their teams and players across several leagues at once. SportsBot brings the numbers to where they already are: a Discord server. Ask it for a player or a team and it answers in the channel; subscribe a channel and it posts updates on its own.

It was the semester project for [CS 222, Software Design Lab](/courses/cs-222/), built by a group of four. The proposal was for soccer, under the working title Soccer Stats for Discord.

## What it was planned to do

| Command | What it does |
| --- | --- |
| `/stats` and a player or team name | Shows that player's or team's statistics for the current season. |
| `/subscribe` and a player or team name | Posts updates for them in the channel automatically. |
| `/unsubscribe` and a name | Stops those updates. |
| `/subscriptions` | Lists everything the channel is subscribed to. |

## How it fits together

<Figure src="/media/projects/sportsbot/architecture.webp" alt="Several Discord servers feed the Discord Gateway API, which feeds a request handler in the backend. The request handler talks to a SQLite database and to an outside sports data API." caption="The architecture diagram from the proposal." />

A Discord bot is one program, so the interface and the backend live in the same Python process and call each other directly. A request first checks a small SQLite database for a recent answer. Only if there is none does it go out to the sports data service, clean up what comes back, and store it.

<Note title="Why cache at all">
The free sports data services limit how often they can be asked. Keeping the latest answers means ten people asking about the same match costs one request, not ten.
</Note>

Live updates were the hard part to plan. The services that push scores as they happen all cost money, so the plan was to ask a free one on a schedule instead, without blocking the bot while it waits, using Python's asyncio.

## How the team planned to work

The four of us split into two pairs: one for the data (requests to the sports service, the database, subscriptions) and one for the Discord side (commands, formatting, how results are shown). I was in the second.

- A new branch for each small feature every week, reviewed by the other member of the pair before merging.
- Tests in pytest, run automatically on every push, with merging blocked while they fail.
- One style for the whole codebase, checked by a linter and fixed by a formatter.
- A ten-week schedule with the first big milestone at week six: a single request working end to end.

The proposal also named what could go wrong: rate limits on free services, player data too detailed to clean up quickly, and subscriptions that do not scale. For each it gave what it would cost and what to cut.
